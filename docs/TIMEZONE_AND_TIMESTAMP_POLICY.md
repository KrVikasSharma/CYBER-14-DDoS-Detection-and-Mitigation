# CYBER-14: Timezone, Timestamp Semantics & Presentation Policy

**Document Version:** 1.0.0  
**Status:** Frozen & Approved  
**Target Timezone:** `Asia/Kolkata` (IST: UTC+05:30)  
**Storage Standard:** UTC (`+00:00`)  

---

## 1. Executive Summary

CYBER-14 enforces an enterprise-grade timestamp architecture:
1. **Database & Storage Layer:** Consistent **UTC** (`+00:00`). All tables store dates in UTC without local offsets.
2. **Backend Processing Layer:** Timezone-aware UTC handling via centralized `app.core.time` utilities. Ambiguous naive datetime calls are strictly prohibited.
3. **API & Serialization Layer:** All timestamps emitted across REST endpoints and WebSocket frames are strictly formatted in ISO-8601 with explicit `'Z'` suffix (e.g., `2026-09-22T02:51:45Z`).
4. **Control Room Dashboard (Frontend):** All timestamps are converted and displayed in **India Standard Time (`Asia/Kolkata`, UTC+05:30)** using browser locale standards (`Intl.DateTimeFormat`).
5. **No Blind Data Manipulation:** Stored records are never artificially shifted by adding hours, and `latency_ms` remains a duration in milliseconds, never conflated with timestamps.

## 2. Semantic Separation of Timing Fields

To prevent ambiguity, CYBER-14 maintains a strict distinction between event time, processing duration, and persistence time:

| Concept | Field | Type | Description |
| :--- | :--- | :--- | :--- |
| **Observation Event Time** | `traffic_events.timestamp` | `DATETIME (UTC)` | Timestamp when the packet or flow observation occurred on the network / was generated by the simulator. |
| **Processing Duration** | `detections.latency_ms` | `FLOAT (ms)` | Monotonic high-resolution execution duration ($t_{\text{end}} - t_{\text{start}}$) of the ML inference pipeline (`perf_counter()`). **Never derived from timestamp subtraction.** |
| **Detection Persistence** | `detections.created_at` | `DATETIME (UTC)` | Timestamp when the detection record analysis completed and was committed to the database. |
| **Incident First Seen** | `attack_incidents.first_seen` | `DATETIME (UTC)` | Flow event timestamp of the *initial* observation triggering this attack incident. |
| **Incident Last Seen** | `attack_incidents.last_seen` | `DATETIME (UTC)` | Flow event timestamp of the *most recent* observation grouped into this incident. |
| **Mitigation Active Window** | `mitigation_actions.started_at` & `expires_at` | `DATETIME (UTC)` | Activation and scheduled expiry timestamps of the defensive policy. `expires_at = started_at + duration_seconds`. |
| **Audit Log Trail** | `audit_logs.created_at` | `DATETIME (UTC)` | Immutable chronological audit timestamp of system and user actions. |

## 3. Database Schema & Column Audit

All 5 core relational tables in `cyber14_ddos` use timezone-aware UTC timestamps:

### `traffic_events`
- `timestamp`: `DATETIME` (Nullable) — Incoming observation event time.
- `created_at`: `DATETIME NOT NULL` — Database insertion time (Default: UTC).

### `detections`
- `latency_ms`: `FLOAT` (Nullable) — Pure processing latency duration in milliseconds.
- `created_at`: `DATETIME NOT NULL` — Detection completion & persistence time (Default: UTC).

### `attack_incidents`
- `first_seen`: `DATETIME NOT NULL` — Event timestamp of first detection for this incident.
- `last_seen`: `DATETIME NOT NULL` — Event timestamp of latest detection for this incident.
- `created_at`: `DATETIME NOT NULL` — Record creation time (Default: UTC).
- `updated_at`: `DATETIME NOT NULL` — Record update time (Default: UTC, onupdate: UTC).

### `mitigation_actions`
- `duration_seconds`: `INT` (Nullable) — Explicit mitigation window (e.g., 300s).
- `started_at`: `DATETIME NOT NULL` — Effective start time (Default: UTC).
- `expires_at`: `DATETIME` (Nullable) — Calculated expiration time (`started_at + duration`).
- `revoked_at`: `DATETIME` (Nullable) — Manual or policy revocation time.
- `created_at`: `DATETIME NOT NULL` — Record insertion time (Default: UTC).

### `audit_logs`
- `created_at`: `DATETIME NOT NULL` — Audit log creation time (Default: UTC).

## 4. Backend Implementation Architecture

### Centralized Authority: `app.core.time`
To avoid scattering naive `datetime.now()` calls or ad-hoc timezone conversions across the codebase, all timing logic is centralized:

```python
from datetime import datetime, timezone
from zoneinfo import ZoneInfo

IST_TIMEZONE = ZoneInfo("Asia/Kolkata")

def now_utc() -> datetime:
    """Single centralized authority for current UTC datetime."""
    return datetime.now(timezone.utc)

def format_iso_utc(dt: datetime | None) -> str | None:
    """Format any datetime to ISO-8601 with mandatory 'Z' suffix."""
    if dt is None:
        return None
    if dt.tzinfo is None:
        dt = dt.replace(tzinfo=timezone.utc)
    else:
        dt = dt.astimezone(timezone.utc)
    return dt.strftime("%Y-%m-%dT%H:%M:%SZ")

def parse_iso_to_utc(val: Any) -> datetime | None:
    """Parse string/timestamp into timezone-aware UTC datetime."""
    ...
```

### Database Connection Configuration
In `app.db.database`:
The SQLAlchemy engine establishes PyMySQL connections with an explicit session initializer:
```python
engine_kwargs["connect_args"] = {"init_command": "SET time_zone = '+00:00'"}
```
This guarantees that regardless of the host operating system's timezone (e.g. Windows set to India Standard Time), MySQL functions (`NOW()`, `CURRENT_TIMESTAMP`) operate strictly in UTC.

## 5. MySQL Server & MySQL Workbench Guidance

### Why MySQL Workbench Displays UTC
MySQL `DATETIME` fields store literal date/time digits without timezone offsets.
When Python inserts a record at `09:15:00 IST`, the UTC value is `03:45:00 UTC`. MySQL Workbench connects and displays:
```
2026-09-22 03:45:00
```
This is **correct** behavior: MySQL is faithfully preserving the canonical UTC storage format.

### Querying in IST from MySQL Workbench
Presenters and database administrators inspecting tables in MySQL Workbench can convert timestamps to IST dynamically:

```sql
-- View detections with IST conversion:
SELECT 
    id, 
    traffic_event_id, 
    latency_ms,
    created_at AS utc_stored,
    CONVERT_TZ(created_at, '+00:00', '+05:30') AS created_at_ist
FROM detections
ORDER BY id DESC
LIMIT 10;
```

```sql
-- View attack incidents in IST:
SELECT 
    incident_id, 
    attack_type, 
    occurrence_count,
    CONVERT_TZ(first_seen, '+00:00', '+05:30') AS first_seen_ist,
    CONVERT_TZ(last_seen, '+00:00', '+05:30') AS last_seen_ist
FROM attack_incidents
ORDER BY id DESC
LIMIT 5;
```

## 6. Frontend Dashboard Conversion Strategy

### Utility: `dashboard/frontend/src/utils/time.js`
The frontend uses standard JavaScript internationalization APIs to convert UTC ISO-8601 strings into `Asia/Kolkata` time:

```javascript
export const IST_TIMEZONE = 'Asia/Kolkata'

export function parseUTC(value) {
  if (!value) return null
  let str = String(value).trim()
  if (str.includes(' ') && !str.includes('T')) str = str.replace(' ', 'T')
  if (!str.endsWith('Z') && !str.match(/[+-]\d{2}:?\d{2}$/)) str += 'Z'
  return new Date(str)
}

export function formatTimeIST(value) {
  const d = parseUTC(value)
  if (!d) return 'N/A'
  return d.toLocaleTimeString('en-IN', {
    timeZone: IST_TIMEZONE,
    hour: '2-digit',
    minute: '2-digit',
    second: '2-digit',
    hour12: true,
  })
}

export function formatDateTimeIST(value) {
  const d = parseUTC(value)
  if (!d) return 'N/A'
  return d.toLocaleString('en-IN', {
    timeZone: IST_TIMEZONE,
    day: '2-digit',
    month: 'short',
    year: 'numeric',
    hour: '2-digit',
    minute: '2-digit',
    second: '2-digit',
    hour12: true,
  }) + ' IST'
}
```

### UI Integration Points
1. **Live Traffic Real-time Stream:** Event table displays time formatted via `formatTimeIST` (e.g. `09:15:22 am`). Flow Drawer displays full `formatDateTimeIST` (e.g. `22 Sept 2026, 09:15:22 am IST`).
2. **Live Graph Timestamps:** X-axis timestamps on real-time continuous SVG charts display in IST.
3. **Detection History:** Table displays timestamps in IST with hover tooltips displaying complete date/time.
4. **Attack Incidents:** `first_seen` and `last_seen` display in IST. Modal details show complete formatted IST timestamps.
5. **Mitigation Control:** `started_at` and `expires_at` display in IST.
6. **Audit Logs:** Log entry timestamps display in IST.
